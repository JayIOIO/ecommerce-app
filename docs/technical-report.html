01 · Executive summary

Purpose, scope, and claims

EcomApp is a marketplace demonstration with buyer and seller experiences backed by separate authentication, product catalog, and order services. The frontend is React with Vite; the APIs are Node.js/Express; data is stored in MySQL. The local feature-stage starter provides the core application modules and a Vite development proxy.

Ash's contribution on this branch supplies a truthful, visible frontend build identifier, build instructions, a manually exercised frontend QA checklist, safe local screenshots, an initial disposable-data integration smoke test, this technical report, and a 15-slide HTML presentation. The UI reads VITE_BUILD_ID at bundle-build time. If unset, it displays “unlabeled build” rather than asserting a false deployment version.

Verified in the local environment

  • All 15 scenarios in the dated frontend checklist were exercised against the local Vite proxy and local APIs using disposable data.
  • Buyer and seller registration/login, catalog search, cart, checkout, order history/cancellation, listing create/edit/delete, seller order view, and fulfillment progression were observed.
  • Buyer UI omitted seller navigation; buyer requests to seller-only APIs returned the expected HTTP 403; buyer order history returned HTTP 200.
  • Frontend lint, frontend production build, backend JavaScript syntax checks, and the local API/database integration smoke test passed on 2026-10-13.
  • All disposable QA users, order data, and products were removed after the run. No passwords or bearer tokens were committed.

Not verified here

  • Operation through the final team reverse proxy. Port 80 responds with a site, but its tested application API routes return 404; HTTPS also presents an untrusted certificate locally.
  • Docker/Compose image build/deploy, Jenkins trigger or quality gate, named-volume persistence, rollback, and CI wiring/review of the local smoke test.
  • A clean-clone README walkthrough by an unfamiliar teammate, a confirmed five-person roster, or merged/pushed status of the current uncommitted documentation changes.
This report separates observed behavior from project requirements and planned work. “Not verified” is not a pass.

03 · Modules and role contracts

Buyer, seller, and service boundaries

Buyer workflow

  1. Register or log in with buyer role.
  2. Search the public catalog; add products to cart.
  3. Provide shipping address/payment choice and place an order.
  4. Review order details/status and cancel eligible Pending orders.

Seller workflow

  1. Register or log in with seller role.
  2. Create, edit, view, and delete seller-owned listings.
  3. View orders containing owned products.
  4. Advance eligible item fulfillment to Processing, Shipped, Delivered.

Role enforcement observed

Frontend navigation and seller screens are conditional on the signed-in role. That presentation guard complements, but does not replace, backend authorization. In the local test a buyer's authenticated requests to GET /api/products/mine and GET /api/orders/seller returned HTTP 403. Buyer order history returned HTTP 200.

Data integrity paths

The checkout test created an order from selected products and quantities; the buyer could read the order and the owning seller could see the item. Seller fulfillment changed the item status through Processing, Shipped, and Delivered, which then appeared in buyer history. A separate Pending order was cancelled through the UI. These are observed local application behaviors, not a substitute for a formal API contract or cross-service automated test.

Real test-account identifiers and synthetic shipping details are intentionally omitted from this report. The private session note stores identifiers for QA traceability only.

04 · Technology and data

Stack rationale and persistence boundaries

TechnologyUse in current checkoutReason tied to this application
ReactBuyer and seller single-page UIComposable role-aware screens and local state for cart/forms.
ViteFrontend development/build tool and local `/api` proxyServes the UI locally and routes service prefixes to separate API processes.
Node.js / ExpressThree separate HTTP APIsKeeps authentication, catalog, and order responsibilities distinct.
MySQLShared relational persistenceForeign keys model users, seller products, orders, and order items.
JWTAuthenticated role-bearing requestsAllows protected catalog/order routes to distinguish buyer and seller capabilities.

Data model (checked-in schema)

users own products and buyer orders. products.seller_id relates inventory to a seller. checkout_orders.user_id relates a checkout to its buyer; order_items connects each order to products and seller ownership. Foreign keys constrain references; order items cascade with their parent order, while product deletion is restricted when referenced by order history.

Configuration and persistence

Services load local environment configuration from the repository-root `.env`, connect to a local MySQL instance, and use the checked-in initialization SQL for schema/seed setup. The root `npm run dev` starts application processes only; it does not start MySQL. `.env` is private and must not be committed.

A persistent named Docker volume, container restart proof, migration path, and rollback persistence behavior are course requirements for a later integrated phase. None was exercised by this feature-stage checkout.

05 · Setup and quality checks

Reproducing this local stage

  1. Install Git, Node.js 22 LTS (or compatible current Node), npm, and local MySQL.
  2. Copy `.env.example` to `.env`; set local DB values and a private JWT secret.
  3. Initialize the schema using `db/init.sql` against the configured MySQL instance.
  4. Run npm run setup, then npm run dev.
  5. Open the frontend and use synthetic, unique buyer/seller accounts.

07 · Build identity and evidence

Version label tied to the bundle source

The sign-in screen and authenticated header display VITE_BUILD_ID, compiled by Vite into the frontend bundle. An unset value renders “unlabeled build.” This avoids embedding an unsupported number or release claim into the UI.

Reproducible local build-label check

$env:VITE_BUILD_ID = 'local-qa-20261013' npm run build:frontend npm --prefix frontend run preview -- --host localhost --port 4173 # Open http://localhost:4173 and inspect the login screen

The `local-qa-20261013` label was visually checked in both sign-in and signed-in screens; screenshots are included in the evidence folder. The disposable account used for the authenticated screenshot was deleted after capture.

Release pipeline hand-off

  • CI must pass the immutable checked-out commit or release identifier as VITE_BUILD_ID before frontend image compilation.
  • A runtime environment change cannot modify an already built static bundle.
  • Do not use a manually selected build number or use HEAD as a claim when uncommitted changes are in the image.
  • After merge/deploy, verify the browser label through the final proxy against the actual image/commit used by CI.
